# Collect source compiled site and SQL evidence

Use this handoff with an authorized agent inside the environment that owns the
application and database exports. Collect repository source, the existing compiled
ASP.NET publication, and an offline SQL schema script. Keep their provenance and
coverage separate while identifying the connections the installed tool can prove.

For a new web + framework + existing publication collection, start with the
[compiled workspace guide](WORKSPACE_COMPILED_GETTING_STARTED.md). It collects web
source and compiled inputs together, scans framework source separately and
combines the raw indexes. The retained-source attachment sections below describe
the distinct case where an existing source scan must stay immutable.

The source and compiled-site workflow exists. General private SQL-dump admission
into that same workflow is a remaining integration task. Supplying DDL to an agent
does not by itself add admitted SQL contracts to a TraceMap index.

## Current capabilities

| Input or operation | Supported behavior | Boundary |
| --- | --- | --- |
| Repository source | `scan` produces a manifest, facts, SQLite index, report and analyzer log. | Project loading, syntax fallback, exclusions and budgets affect coverage. |
| Existing compiled ASP.NET site | Native `webforms-review` supports fresh collection or attachment to a retained source scan, with explicit assemblies and binding/publication evidence. | Build correspondence must be supplied and checked; missing evidence remains a gap. |
| Source and compiled combination | Native attach scans compiled inputs separately and combines the retained source and compiled indexes with explicit attachment bindings. | The original source scan stays immutable. |
| Ordinary `.sql` files | The scanner inventories SQL text and supported query shapes. | This is not a complete database catalog or stored-procedure result contract. |
| Bounded SQL Server DDL contracts | Separate producers compare supported procedure parameters, constant result projections, and restricted table-backed result projections against source evidence. | The documented routes admit public synthetic inputs. They are not a general private catalog importer or an automatic third input to native Web Forms review. |

## Files to locate

Record actual private paths in a local collection summary. Do not select files by
newest modification time or reconstruct their identities from remembered names.

| File | Purpose |
| --- | --- |
| `config/webforms-review.jsonc` under an old review root | Legacy source-pipeline configuration. It identifies source scopes, project selection and page selection. |
| `scripts/Run-FocusedWebFormsPageList.json` | Local helper settings containing `indexPath`, `outputRoot` and `forms`. Copy the checked-in `.example.json` only when creating new settings; this file reads existing evidence rather than configuring collection. |
| `configuration/review-config.local.json` under an imported proof verification root | Native source/compiled configuration generated by retained-proof import. A manually authored native config may have another filename. |
| `root.config.json`, project `project.config.json` and `native.config.json` | Configuration produced by the native terminal wizard. Preserve the whole configuration root. |
| `scan-manifest.json`, `facts.ndjson`, `index.sqlite`, `report.md`, `logs/analyzer.log` | Retained source-scan artifacts. Preserve them together. |
| `publish-receipt.local.json` and `compiled-binding.local.json` | Existing proof inputs when using the retained-proof migration route. Preserve their original folders and declared input bytes. |
| `run-manifest.json`, checkpoints and the selected report attempt | Native run state and the bindings for its admitted artifacts. |
| An owner-selected `.sql` schema export | Database definitions. There is no universal required dump filename in this workflow. |

Missing receipts or deleted source/publication inputs cannot be repaired by
inventing hashes or copying manifest rows. Use fresh collection when retained
provenance cannot be established.

## Establish the collection scope

1. Record the installed TraceMap build identity and source revision separately
   from the extractor-version manifest printed by `tracemap versions`. For a
   source checkout, record `git rev-parse HEAD` in that checkout and establish
   which binary was built from it. Follow the installed CLI's help and matching
   contracts.
2. Obtain the source repository path, exact commit, project/solution selection,
   required source folders, and requested page scope from the owner.
3. Obtain the existing published **site root containing `bin`**, its selected
   managed assemblies and dependencies, available PDBs/maps, and receipts.
4. Obtain the existing offline SQL script and its export scope. Determine whether
   it includes procedure/function/view definitions and their dependent table/type
   definitions, rather than tables alone. Keep any row-data export outside this
   collection unless separately required and authorized.
5. Choose fresh output folders outside source, publication and the TraceMap
   checkout. Preserve existing successful and failed runs.

An all-pages selection is not evidence that every repository/project or published
compiler input was covered. The wizard selects a website project; it does not
automatically register an entire monorepo. Explicitly account for backend/shared
projects and any separately scanned repositories.

## Collect or reuse the source scan

For a new repository scan, a minimal PowerShell invocation is:

```powershell
$SourceRepo = 'C:/source/WebApp'
$SourceScan = 'C:/reviews/WebApp-collection/source-scan'
tracemap scan --repo $SourceRepo --out $SourceScan
```

Supply an appropriate `--solution` or repeated `--project` selection when needed.
Confirm inventory, selected projects, exclusions, build status and analysis gaps
against the requested scope. A failed build or a reduced scan stays labeled as
such. Do not add restore/build execution merely to hide a gap.

For an existing scan, verify its retained identity and complete artifact set
before reuse. Do not modify its SQLite database or append compiled/SQL facts.

## Attach the existing compiled site

Keep the two source pipelines separate from compiled attachment. The legacy
`Merge-FocusedWebFormsReview.ps1` combines web and backend source scans. The
native **attach** operation instead takes a retained source scan, collects a
separate compiled-only scan, then creates a receipted combination. Native
**fresh** collects source and compiled inputs together. These are distinct routes;
a generic multi-source merge does not establish compiled attachment bindings.

Use [Native compiled Web Forms workflow](WEBFORMS_NATIVE_WORKFLOW.md), especially
its configuration contract and fresh/attach sections. For attach, prepare a full
strict native JSON config with these settings:

| Setting | Value to establish |
| --- | --- |
| `schemaVersion` | `webforms-compiled-review-config.v1` |
| `operation` | `attach` |
| `parentScanRoot` | Exact retained source-scan folder |
| `sourceRoot`, `sourceCommitSha` | Source identity checked against the retained parent |
| Project, source-folder and page fields | Explicit requested application scope |
| `publishedRoot` | Existing published site root, not its `bin` subfolder |
| Assembly, dependency, PDB and map fields | Explicit files from the owner-selected publication inventory |
| Binding and publish receipt fields | Existing admitted receipts or inputs for authorized native preparation |

This table is not a complete JSON template. Use the full current contract; reject
unknown fields. In particular, do not invent a `sqlSchema` property.

If an old proof survives, follow
[Reuse the unchanged retained publish proof](WEBFORMS_CONFIG_MIGRATION.md#reuse-the-unchanged-retained-publish-proof).
Otherwise configure a fresh collection or explicit attach using the native guide.
Receipt preparation requires an owner declaration of exact source/publication
correspondence; an agent must not infer that correspondence from similar names.

With a prepared native config, the entry point is:

```powershell
tracemap webforms-review start `
  --config 'C:/reviews/WebApp-collection/configuration/review-config.local.json' `
  --out 'C:/reviews/WebApp-collection/compiled-review'
```

Replace all example paths with the selected inputs. If preparation is needed,
follow the native guide's explicit attestation option. Do not rebuild or launch
the website as an incidental step.

After execution, inspect `webforms-review status --run <printed-run-root> --json`.
Use the exact checkpointed report attempt. Its `combined.sqlite`, handoff and
`review-evidence.sqlite` are different artifacts: the combined index contains
combined scan evidence; the evidence index supports bounded retained-document
queries. Preserve both with the run state.

Do not use a combined index as though it were an original single-scan input.
Native attach supplies explicit compiled-attachment bindings during combination;
an arbitrary merge or direct SQLite edit is not a substitute for that admission.

## Collect the SQL channel and determine its status

Keep the offline dump alongside the private collection, outside the public
TraceMap checkout. Record its actual file hash, source/export identity, scope and
known omissions in the local summary. Parse definitions only; do not execute the
dump, procedures or application methods, or initiate a database/catalog connection
as an incidental collection step.

First identify the intended evidence:

- Procedure parameters need declarations of names, types, sizes and directions.
- Returned column shapes need the selected procedure's projection and applicable
  table/view/type definitions. A table's columns are not automatically the columns
  a procedure returns.
- Runtime-selected SQL, branches, temporary objects, dynamic SQL and external
  dependencies can leave a shape unknown even when a dump is available.

Audit the installed importer against these current bounded contracts:

- [DDL parameter evidence](validation/SQLSERVER_DDL_PARAMETER_EVIDENCE.md).
- [Result-column evidence](validation/SQLSERVER_RESULT_COLUMN_EVIDENCE.md).
- [Table-backed result shapes](validation/SQLSERVER_TABLE_RESULT_EVIDENCE.md).
- [Public SQL acceptance and remaining private-schema prerequisite](validation/SQLSERVER_PUBLIC_ACCEPTANCE.md).

The table-backed route supports a narrow explicit-column, single-table SELECT
subset. Joins, views, filters, dynamic SQL and many ordinary dump statements remain
unsupported. The documented producers require independently authored public
synthetic inputs. **Do not mark a work dump `publicSynthetic: true` or use a public
synthetic export as evidence for the work database.**

If the authorized work checkout has an additional private importer, identify its
implementation revision, accepted format, generator/input hashes, output schema,
rules, limitations and binding tests. Establish that route before using it.
Otherwise retain the dump as a separate evidence channel and report the missing
private admission/integration capability. A generic `.sql` scan supplies inventory
facts, not a substitute for accepted procedure contracts.

The separate `--sql-validation-summary` option consumes validator observations
for the [SQL operator packet](SQL_OPERATOR_RUNBOOK_PACKET.md). It is not a DDL
dump importer or a procedure-result-shape input. Do not substitute that contract
for the missing schema admission route.

Keep any agent-inferred shape in the human interpretation section, citing the
relevant local SQL file and line spans. Do not insert it as a native fact or claim
that three channels are already joined in one database. A private importer or
versioned workflow extension is a separately scoped implementation task, using
synthetic regression fixtures and explicit source-call-to-contract bindings.

## Deliver the collection to the work agent

Produce one private `COLLECTION_SUMMARY.local.md` with:

1. Tool versions, exact source revisions and selected scope.
2. Exact source, compiled run, checkpoint/report and offline SQL input locations.
3. Which artifact is a raw scan index, a combined index or a retained-document
   evidence index; retain their existing receipts and hashes.
4. Per-channel coverage, omissions, failures and unsupported shapes.
5. For one selected event-to-database route, the fact IDs, rule IDs, evidence tiers,
   spans and source identities behind each connection. Mark unknown edges in any
   Mermaid diagram.
6. SQL status: **collected only**, **admitted by an identified importer**, or
   **bound to the selected call**. List the exact missing inputs/capability for the
   next state.

Keep private contents, identities and input fingerprints inside the authorized
environment. New derived machine-readable evidence must identify its exact
generator SHA-256 and bounded input SHA-256; shareable outputs may hash only their
privacy-projected input. Do not fabricate a native receipt or publish an agent's
interpretation as scanner evidence.

The collection is ready for review when all three channels are accounted for,
including an explicit SQL integration gap if that capability is unavailable.
Runtime behavior and a complete application migration remain separate claims.
