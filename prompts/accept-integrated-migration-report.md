# One integrated WebForms / SQL / outbound HTTP acceptance

Use the branch revision supplied by the operator. This is one focused acceptance
run, not repeated parameter-field debugging. All private inputs and results stay
on the work machine. Do not modify application code, execute application methods,
connect to a database, export patches, commit or upload artifacts.

1. Confirm the saved project configuration and resolved source root locally with
   the operator. Never infer the repository from previous debugging context.
2. Build the selected public TraceMap checkout. Reuse an existing scan only if it
   was produced by this revision and contains the Integrated migration inventory
   section. Otherwise run one already-authorized focused scan using the saved
   project configuration. Do not guess new flags or change root selection.
3. Inspect report.md: Integrated migration inventory and Incoming boundary
   coverage. This report covers supported source operation facts across the scan,
   including operations not connected to a selected entry point. It is not a
   complete runtime/business-operation denominator. SQL and outbound HTTP are
   separate families; WebForms markup is not a deployed URL.
4. For one page/control entry and one unconnected operation, verify fact references,
   ordered candidate hops, source locations and tiers against local source. Never
   splice source paths with historical compiled paths. Keep compiled wrapper
   evidence in its existing admitted grouped report until an explicit identity
   bridge is established. Missing/ambiguous edges remain unresolved.
5. Check that parameter rows group under the observed operation location rather
   than being counted as separate SQL operations. Inspect value observations,
   text trace status, and the pending contract/authorization/transaction questions.
   Same-line ambiguous operations must not receive invented parameter mappings.
6. Return only operator-approved counts: operation evidence groups by family;
   WebForms bindings/handler resolutions; groups with candidate entry paths;
   unconnected groups; ungrouped parameter facts; explicit caps/limits; and any
   failed evidence joins. No names, paths, SQL, values, hashes, source or screenshots
   are required. Do not report unsupported shapes as zero merely because the
   expected parameters were captured.

Acceptance means the integrated report accurately exposes known paths, independent
operations and remaining gaps. It does not require all conservative fields to be
positive, and does not approve API implementation or retire existing behavior.

If a locally known entry-to-operation chain remains unconnected, use
[the complete-chain diagnostic prompt](diagnose-integrated-entry-path-gap.md)
against the existing scan. Accurate gap reporting is not connectivity acceptance.

For a previously diagnosed Handles chain, explicitly report whether that exact
chain now appears. Read its `anchor assessment` and the aggregate Handles anchor
assessment counts. If rejected, inspect only the first reported guard against
local facts/source and return its generic reason plus sanitized structural shape
(for example, base declaration in a separate partial file or an imported short
base spelling). Do not treat accurate gap reporting as a passed connectivity fix.
If the anchor is established but no path appears, diagnose the downstream hop or
search limit instead. Use the existing scan after this one acceptance run; no
repeated rescans. Keep private type names, paths, source and fact IDs local.
