# Deep projectless cross-DLL regression

Public synthetic code only. Do not execute the fixture's database methods.

The scanned website source is `samples/messy-dotnet-workspace/vb-deep-projectless`:
it contains no project. This external build harness produces a net48 website
method DLL and a separate `PublicProof.Framework.dll`. The provider contains
real VB compiler output for byref arrays, struct addresses, debug field stores,
mapping loops, timeout/transaction setters and overload forwarding.

Run from the repository root on macOS or Windows:

```text
dotnet test src/dotnet/tests/TraceMap.Tests/TraceMap.Tests.csproj --filter FullyQualifiedName~Deep_projectless --verbosity minimal
```

Build just the corpus on Windows (or macOS):

```text
dotnet build samples/fixture-build/deep-projectless/DeepWebsite.vbproj
```

The test scans the projectless source with both compiled inputs, writes a SQLite
index, combines it, and invokes the actual path reporter. It checks twelve
ordered forwarding layers, both assembly identities, the Fill terminal and
caller-substituted command-text/type candidates. Mixed and compiled-only queries
are covered; missing-provider and insufficient-depth queries must not invent a
completed route. Branches retain distinct procedure fingerprints; cycles are
reported, same-named decoys are excluded, unknown text and computed-Boolean
operand limitations are not promoted to constants. Repeated compiled queries
pin method-sequence/value determinism without equating cross-scan IDs.

The native-workflow case commits synthetic source in an isolated repository,
then compiles those exact inputs using external projects. It runs native
preparation/start, restores the grouped handoff, queries the saved combined
index with one handler and compiled-only scope, and checks byte-identical resume.
Both DLLs are primary in this case because both were compiled from the committed
synthetic source. That is not authority to bind an unrelated private provider.
Its `.compiled` map is generated by the test, not by ASP.NET.

The query tests cap traversal at 100,000 work units, graph payload reads and
scratch storage at 32 MiB, generated scan/index artifacts at 32 MiB, and local
scan/index/query elapsed time at a generous 60 seconds. Native rendered documents
are capped at 32 MiB each, evidence SQLite files at 64 MiB each, and the complete
retained native root at 128 MiB. These are not physical drive-I/O measurements.

The broad five-handler mixed-source native report previously exhausted the
100,000-work budget with no paths. Encoded IL transitions now take priority;
a reverse terminal-distance pass prunes branches unable to finish inside the
configured depth. Its key/reference work is charged to the same global budget,
state is frontier-bounded, and an incomplete pass is discarded rather than used
to hide paths. The native regression pins all five handlers and six expected
routes under 1,000 work units (observed 391), with the exact deep chain and
command text/type candidate. Depth/cycle gaps remain explicit and partial.
This is not exhaustive mixed/compiled parity or a physical drive-read claim.

## Retained validation and Windows handoff

The wrapper preserves a test-result file and a generator/input-hashed local
validation receipt. Existing output folders are refused; failed output is retained.

```powershell
.\scripts\validation\Test-DeepProjectlessCorpus.ps1
```

On Windows with .NET SDK, PowerShell 7 and the ASP.NET Framework 4 compiler:

```powershell
.\scripts\validation\Test-DeepProjectlessCorpus.ps1 -RequireWindowsPublish -OutputRoot "$env:USERPROFILE\tracemap-deep-corpus-1"
```

This adds real mapped and updatable/mapless ASP.NET publishes, validates artifact
hashes and the exact cross-DLL command chain, and retains both small published
corpora. Return the output folder (including `tests/deep-corpus.trx`,
`validation.local.json`, `publish-mapped`, `publish-mapless`, and separate
provider PDBs) for inspection. On macOS the authentic publish test is an explicit
skip; a successful local run cannot satisfy `-RequireWindowsPublish`.

Limitations: the normal harness is not an ASP.NET precompiler publish. Authentic
website publishing is only exercised by the Windows tests; the separate provider
is built by the SDK VB compiler targeting net48, not by the private vendor's
historical compiler. Parameter-value propagation,
runtime branch feasibility, provider execution and private migration completeness
remain unproven. A static command candidate is not database execution proof.
